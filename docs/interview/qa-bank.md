# MotionEdge-F103 高频追问题库（60 题）

回答顺序统一为：先结论，再落到项目，解释选择，最后给出升级方向。每题适合 20–60 秒回答。

## A. C / Embedded（10 题）

### Q1. 为什么固件不用动态内存？

- **一句话回答：** 为了让 RAM 上界、失败模式和实时行为可预测。
- **项目实现：** Task、Queue、Mutex、Event Flag、DMA 和协议缓冲均静态分配，禁止 `malloc/calloc/realloc`。
- **为什么这样设计：** F103 RAM 小，长期运行不应承担碎片、不可控延迟和分配失败。
- **继续优化：** 用链接 map、stack high-water 和静态 RAM 表继续做预算，而不是引入堆。

### Q2. `volatile` 在这个项目里解决什么？

- **一句话回答：** 它告诉编译器对象可能被正常控制流之外修改，但不提供原子性或线程安全。
- **项目实现：** DMA 计数器、ISR/外设状态通过 HAL/BSP 读取；任务共享数据主要用 Mutex/Queue，而不是只加 `volatile`。
- **为什么这样设计：** 可见性、原子性和互斥是不同问题，不能用一个关键字代替同步设计。
- **继续优化：** 对真正 ISR 共享字段审计访问宽度和临界区，保持共享模型最小。

### Q3. 为什么大量对象声明为 `static`？

- **一句话回答：** `static` 限制链接可见性并提供确定生命周期。
- **项目实现：** Service 状态、静态任务控制块、Stack 和固定缓冲只在所属模块内部可见。
- **为什么这样设计：** 防止跨模块随意写状态，也避免大数组落在任务栈上。
- **继续优化：** 对只读表再使用 `static const`，但不会把可变状态错误改成 const。

### Q4. 如何防止数组越界？

- **一句话回答：** 先建立协议/缓冲理论上界，再在每层检查 length 和返回值。
- **项目实现：** Parser 限制 payload，CommandService 校验命令长度，队列复制取最小容量，BSP DMA 维护固定容量和溢出计数。
- **为什么这样设计：** 串口输入不可信，边界检查必须在消费前完成。
- **继续优化：** 对 parser 做更多 fuzz/property test，并让静态分析进入 CI。

### Q5. 32 位毫秒计数回绕怎么处理？

- **一句话回答：** 用无符号差值比较持续时间，不比较绝对时间大小。
- **项目实现：** timeout 采用 `(uint32_t)(now - then) > limit`，Python 验收也有 uint32 counter delta 测试。
- **为什么这样设计：** 模运算能在一次回绕范围内保持正确，而直接 `now > deadline` 容易出错。
- **继续优化：** 为每个 timeout helper 增加边界向量，并限制任何区间远小于 2^31 ms。

### Q6. 为什么算法模块不调用 HAL？

- **一句话回答：** 让算法只依赖数据和时间步，便于主机测试与平台迁移。
- **项目实现：** Low-pass、Attitude、PID 位于 `Algorithms/`；HAL 只在 BSP/驱动适配层。
- **为什么这样设计：** 数学正确性不应依赖 STM32 外设，故障定位也更清晰。
- **继续优化：** 保持接口 POD 化，在换 MCU 时只替换 BSP 和构建适配。

### Q7. 如何处理函数返回值？

- **一句话回答：** 任何可能失败的硬件、协议和状态转换都显式检查。
- **项目实现：** I²C/UART/PWM/Flash BSP 返回状态；Service 将失败转换为 degraded、fault 或安全拒绝。
- **为什么这样设计：** 忽略失败会让上层继续使用无效姿态或危险输出。
- **继续优化：** 给关键错误增加 fault tree，区分可恢复、降级和必须 ESTOP 的路径。

### Q8. 大结构体为什么不用值传递到处复制？

- **一句话回答：** 大对象通过 const 指针或受保护 snapshot 传递，减少 Stack 和复制时间。
- **项目实现：** MotionFrame 通过 Service snapshot/Mutex 获取；协议 payload 在固定边界内复制。
- **为什么这样设计：** F103 RAM 紧张，跨任务又需要一致快照，不能只追求少写几行代码。
- **继续优化：** 用 map 和 stack usage 证据评估复制热点，不做无测量的零拷贝重构。

### Q9. 如何处理非有限浮点数？

- **一句话回答：** 在控制边界拒绝 NaN/Inf，进入安全状态而不是让它传播到 PWM。
- **项目实现：** PID/ControlService 有 nonfinite guard 和计数，输出还经过整数化与绝对 PWM clamp。
- **为什么这样设计：** 与 NaN 比较常返回 false，单靠上下限判断可能失效。
- **继续优化：** 增加更多异常输入 fuzz，并保留最终物理范围的独立防线。

### Q10. Debug 和 Release 编译策略为什么不同？

- **一句话回答：** Debug 优先可调试，Release 优先尺寸；v1.0.1 只压缩稳定运行库。
- **项目实现：** Application Debug 是 `-Og -g3`，HAL/FreeRTOS Debug 是 `-Os -g3`，Release 是 `-Os -g0`，均启用 section GC。
- **为什么这样设计：** 既保留应用断点和源码定位，又释放 3068 B Debug Flash。
- **继续优化：** 只有资源再次逼近门限才单独评估 LTO，并要求实机与调试验证。

## B. STM32（10 题）

### Q11. 为什么选择 STM32F103C8T6？

- **一句话回答：** 它能覆盖本项目外设和实时控制，同时资源约束迫使设计可审计。
- **项目实现：** 使用 I²C1、USART1+DMA、TIM3 PWM、TIM4 timebase、SWD 和 64 KiB Flash。
- **为什么这样设计：** 板卡成熟、工具链完整、教学资料多，适合从底层到工程化完整实现。
- **继续优化：** 若加入 TLS、双 IMU 或复杂滤波，优先迁移到更高 RAM/Flash MCU。

### Q12. 为什么使用 CubeMX 生成初始化？

- **一句话回答：** 用官方工具固化时钟、引脚、DMA 和中断配置，用户代码专注业务层。
- **项目实现：** `.ioc`、`Src/Inc` 和生成 CMake 由 CubeMX 管理，用户模块单独列入构建。
- **为什么这样设计：** 降低手写 startup/linker/外设初始化错误，并可从配置复现。
- **继续优化：** 更新 `.ioc` 后审查 generated diff，用户代码仍不进入自动生成区。

### Q13. 为什么 HAL 只放 BSP？

- **一句话回答：** 隔离芯片 API 与业务语义。
- **项目实现：** `bsp_i2c/uart/pwm/flash` 调 HAL；Service 和 Algorithm 使用项目接口。
- **为什么这样设计：** Host C 测试可替换 BSP stub，换 MCU 时改动集中。
- **继续优化：** 为 BSP 接口补硬件 contract 文档和错误映射测试。

### Q14. 为什么 I²C 用 PB6/PB7？

- **一句话回答：** 这是当前 CubeMX 配置的 I²C1 默认引脚，接线简单且已实机验证。
- **项目实现：** MPU6500 地址 `0x68`、WHO_AM_I `0x70`，BSP 有超时与恢复。
- **为什么这样设计：** 不需要重映射即可保留 USART1 和 TIM3_CH1 引脚组合。
- **继续优化：** PCB 化时重新检查上拉、电平、走线和总线电容。

### Q15. 项目到底有没有用 DMA？

- **一句话回答：** USART1 RX 已使用 512 B 循环 DMA；I²C 小批量周期读取和 PWM 不需要额外 DMA。
- **项目实现：** `BSP/bsp_uart.c` 读取 DMA 写指针并维护环形接收，线路错误后重启 DMA。
- **为什么这样设计：** 串口持续字节流最需要降低中断压力；IMU 每 10 ms 小块读取，TIM3 由硬件持续输出。
- **继续优化：** 只有测到 I²C 占用或更高采样率瓶颈，才评估 I²C DMA。

### Q16. 为什么 UART RX 用循环 DMA？

- **一句话回答：** 避免逐字节中断在 RTOS 运行时造成 overflow，并允许批量送入 parser。
- **项目实现：** DMA 固定缓冲、software pending count、overflow counter 和错误恢复都在 BSP。
- **为什么这样设计：** DMA 负责搬运，CommunicationTask 负责解析，职责分离。
- **继续优化：** 用逻辑分析仪和高负载流量测量最坏服务间隔，而不是直接增大缓冲。

### Q17. TIM3 PWM 如何得到 50 Hz？

- **一句话回答：** 定时器预分频到 1 µs 计数，再用 20 ms 周期产生舵机脉冲。
- **项目实现：** TIM3_CH1 PA6 输出，ActuatorService 请求 1450–1550 µs 范围。
- **为什么这样设计：** 1 µs 单位让安全边界和控制输出直接对应寄存器计数。
- **继续优化：** 用示波器验证实际周期和脉宽抖动；当前电气 jitter 未测试。

### Q18. 为什么 HAL timebase 用 TIM4？

- **一句话回答：** 把 HAL 毫秒时基从 SysTick 分离，减少与 FreeRTOS tick 的职责冲突。
- **项目实现：** TIM4 提供 HAL timebase，FreeRTOS 管理任务节拍。
- **为什么这样设计：** RTOS 接管 SysTick 后，阻塞/中断优先级关系更可控。
- **继续优化：** 对中断优先级做自动检查，确保可调用 RTOS API 的 ISR 满足规则。

### Q19. 为什么 Flash 只按 64 KiB 管理？

- **一句话回答：** 正式器件是 F103C8，不能依赖部分芯片可能存在的未声明容量。
- **项目实现：** 应用上限 63488 B，末尾 2048 B 固定给双槽配置。
- **为什么这样设计：** 超规格使用不可移植，也会破坏发布和安全门禁。
- **继续优化：** 需要更多容量时更换明确规格的器件，不修改 linker 欺骗工具。

### Q20. ST-LINK 在项目里不只是下载器吗？

- **一句话回答：** 它同时支持可复现烧录、verify/reset、SWD 调试和发布候选确认。
- **项目实现：** 硬件验收记录 probe、器件、供电电压和下载验证。
- **为什么这样设计：** 把“编译成功”与“目标 MCU 上确实运行该候选”区分开。
- **继续优化：** Demo 前固定 probe/线材并保留一份已验证 HEX 和恢复步骤。

## C. MPU6500 / Attitude（10 题）

### Q21. 为什么选择 100 Hz？

- **一句话回答：** 它是手持动态响应、I²C/CPU 开销和 SG90 演示之间的平衡。
- **项目实现：** SensorTask 10 ms 周期完成采集、融合和控制，Telemetry 降到 10 Hz。
- **为什么这样设计：** UI 不需要 100 Hz 网络数据，但控制需要更细时间步。
- **继续优化：** 用频谱和端到端延迟测量决定是否调整，而不是追求更高数字。

### Q22. 为什么校准 500 样本？

- **一句话回答：** 约 5 s 静止平均能降低随机零偏噪声，又不让启动等待过长。
- **项目实现：** 未完成校准时控制不能 Enable，状态可观测。
- **为什么这样设计：** 样本太少均值不稳，太多会降低可用性且不能修复移动校准。
- **继续优化：** 用方差稳定曲线和静止检测自适应结束，而不是固定堆样本。

### Q23. 为什么 low-pass alpha 是 0.20？

- **一句话回答：** 它来自 Phase 8 候选参数比较，在噪声和动态跟随之间取折中。
- **项目实现：** 配置以 `alpha_milli=200` 保存，最终为 0.20。
- **为什么这样设计：** 更小更平滑但滞后，更大响应快但加速度噪声进入姿态。
- **继续优化：** 在固定动作夹具和可溯源参考下重新扫描，而非主观调参。

### Q24. 为什么 gyro weight 是 0.98？

- **一句话回答：** 短期主要相信陀螺仪，低频用 0.02 加速度计分量约束漂移。
- **项目实现：** Phase 8 选定 `gyro_weight_milli=980`，100 Hz 互补融合。
- **为什么这样设计：** 手持动态中加速度计包含线加速度，不能给它过高瞬时权重。
- **继续优化：** 参数与采样周期相关；改变频率后应重新验证，不机械沿用 0.98。

### Q25. 为什么不用 Kalman？

- **一句话回答：** 当前六轴、100 Hz、F103 资源和可解释性下，互补滤波已经满足展示与实测目标。
- **项目实现：** 状态少、参数 0.20/0.98 可追溯，Debug Flash/RAM 余量仍紧张。
- **为什么这样设计：** Kalman 需要可信模型、噪声协方差和更多验证，不是算法名字越高级越好。
- **继续优化：** 加磁力计/机械模型且有可溯源参考时，再比较 EKF 的收益与资源成本。

### Q26. 为什么只有 Roll/Pitch 没有 Yaw？

- **一句话回答：** 六轴 IMU 的重力参考不能观测绕重力轴的绝对航向。
- **项目实现：** AttitudeEstimator 只发布 Roll/Pitch，避免把陀螺积分当长期绝对 Yaw。
- **为什么这样设计：** 没有磁力计或外部参考时 Yaw 会漂移，输出数字不等于可验证能力。
- **继续优化：** 加磁力计、视觉或编码器并处理硬软铁标定。

### Q27. 0.352°/0.375° 是绝对精度吗？

- **一句话回答：** 不是，是相对 iPhone 水平仪的 MAE，状态为 `REFERENCE_LIMITED`。
- **项目实现：** Phase 8 保存 reference setup、原始 CSV、拟合和排除段，参考不确定度标为 unknown。
- **为什么这样设计：** 被测误差和参考误差无法分离，不能做计量级结论。
- **继续优化：** 使用可溯源角度台并建立安装与不确定度预算。

### Q28. 静态标准差和 MAE 有什么区别？

- **一句话回答：** 标准差描述静止波动，MAE 描述相对参考的平均绝对偏差。
- **项目实现：** Roll/Pitch 静态 std 是 0.019°/0.016°，MAE 是 0.352°/0.375°。
- **为什么这样设计：** 低噪声不代表低偏差，两个指标不能互换。
- **继续优化：** 同时报告 bias、repeatability 和 reference uncertainty。

### Q29. 为什么姿态链需要 timestamp 和 sequence？

- **一句话回答：** timestamp 决定 `dt` 和新鲜度，sequence 检测重复、缺失和新样本。
- **项目实现：** MotionFrame 携带二者，ControlService 拒绝 stale/重复条件，验收统计 continuity。
- **为什么这样设计：** 只有角度值无法判断它是否过期或被重复使用。
- **继续优化：** 对时钟漂移和多传感器同步再引入统一时间基准。

### Q30. 传感器离线时为什么不保持最后输出？

- **一句话回答：** 最后姿态可能已失效，继续驱动比回安全状态风险更大。
- **项目实现：** offline、stale、not calibrated 会阻止 Enable 或触发 ESTOP/Disabled。
- **为什么这样设计：** Fail-safe 优先于短暂“看起来连续”。
- **继续优化：** 机械平台中可根据风险定义受限降级，但必须有独立反馈和 hazard analysis。

## D. FreeRTOS（10 题）

### Q31. 为什么使用 FreeRTOS？

- **一句话回答：** 项目已有多种周期和阻塞边界，RTOS 能明确隔离调度与资源所有权。
- **项目实现：** 四个静态任务、固定 Queue/Mutex/Event Flag、deadline/stack/heap 监测。
- **为什么这样设计：** 比不断膨胀的 super-loop 更容易表达 100/~500/10/1 Hz 和故障隔离。
- **继续优化：** 小功能仍可在现有任务内合并，不因用了 RTOS 就不断加任务。

### Q32. 为什么恰好四个 Task？

- **一句话回答：** 它们对应四种不同节拍和阻塞语义，而不是按模块数量拆任务。
- **项目实现：** Sensor、Communication、Telemetry、Health。
- **为什么这样设计：** 控制任务数可以减少 Stack/RAM 和同步复杂度。
- **继续优化：** 只有出现独立 deadline 或阻塞需求才新增任务，并先给资源预算。

### Q33. 为什么 CommunicationTask 约 500 Hz？

- **一句话回答：** 2 ms 服务周期用于及时搬取 DMA 数据和推进 parser，不是网络频率指标。
- **项目实现：** USART RX 循环 DMA，CommunicationTask 批量消费并生成响应。
- **为什么这样设计：** 降低 backlog 与 command latency，同时不会用逐字节中断占满 CPU。
- **继续优化：** 依据最坏串口吞吐和 task execution time 调整，而不是固定崇拜 500 Hz。

### Q34. 为什么不用额外 ControlTask？

- **一句话回答：** PID 必须紧跟同周期姿态，合并进 SensorTask 更同步、更省 RAM。
- **项目实现：** 100 Hz SensorTask 调用 sensor、motion、control/actuator 单次入口。
- **为什么这样设计：** 新任务会增加 Stack、切换和 sample-to-control 相位不确定性。
- **继续优化：** 真正多速率或高算力控制出现时，再用测量决定拆分。

### Q35. Mutex、Queue、Event Flag 分别解决什么？

- **一句话回答：** Mutex 保一致快照，Queue 传有序命令，Event Flag 广播状态条件。
- **项目实现：** motion/uart/logger mutex、fixed command queue、ready/calibrated/fault flags。
- **为什么这样设计：** 三种对象语义不同，用错会导致丢事件、覆盖数据或无界等待。
- **继续优化：** 保持超时和失败计数，避免把所有同步都变成 blocking queue。

### Q36. 为什么 Task 和 RTOS 对象静态创建？

- **一句话回答：** 在启动前确定 RAM 成本，避免运行时分配失败。
- **项目实现：** `StaticTask_t`、静态 Stack、StaticQueue 和固定 FreeRTOS heap。
- **为什么这样设计：** F103 RAM 余量只有 1120 B，动态行为不可接受。
- **继续优化：** 从 high-water 证据评估，但不因一次观测就把栈缩到极限。

### Q37. 为什么不缩 Task Stack 节省 RAM？

- **一句话回答：** 没有多轮最坏场景证据时，几十字节收益不值得 Stack overflow 风险。
- **项目实现：** v1.0.1 保持所有 Stack 不变；Telemetry 历史最低余量约 200 B。
- **为什么这样设计：** 栈风险可能静默破坏控制和协议，Flash 优化更安全。
- **继续优化：** 覆盖所有日志、错误和配置路径后再按安全裕量提案。

### Q38. Deadline miss 怎么判断？

- **一句话回答：** 记录期望周期与实际运行时刻的偏离/错过，并按任务累计。
- **项目实现：** RtosMonitor 统计 run、deadline、execution/jitter、stack 和 queue。
- **为什么这样设计：** 仅看平均频率会掩盖偶发迟到。
- **继续优化：** 使用更高分辨率计时器获得微秒 WCET；当前 tick 分辨率有限。

### Q39. 最终 Sensor deadline delta=1 是否失败？

- **一句话回答：** 它是 warning，不隐藏，也不能单独等同系统失败。
- **项目实现：** 624.742 s 中 Sensor +1，其余 0；无 reset、fault、数据损坏或控制失败。
- **为什么这样设计：** 评价要同时看事件与后果，并保留可追溯异常。
- **继续优化：** 复现负载条件、提高 timing resolution，定位偶发来源。

### Q40. 600 秒稳定性够吗？

- **一句话回答：** 足够作为阶段功能门禁，不足以证明工业寿命。
- **项目实现：** 分别有 RTOS、MQTT、PID 和 624.742 s 综合验收，场景目标不同。
- **为什么这样设计：** 有限实验只能支持有限结论，不能外推温度、EMC、老化和批次。
- **继续优化：** 建立小时/天级 soak、环境箱、EMC 和多板统计计划。

## E. PID / Control（10 题）

### Q41. PID 为什么 Ki=0？

- **一句话回答：** 因为当前没有舵机输出作用回 MPU6500 的机械外环，持续手持误差不应被积分累积。
- **项目实现：** 完整 PID 支持积分，最终 Kp 1.0、Ki 0、Kd 0.05，integral disabled。
- **为什么这样设计：** 持续 10° 输入时积分只会推到限幅，并不能消除“误差”。
- **继续优化：** 形成真实机械外环后，根据稳态误差和 anti-windup 重新调 Ki。

### Q42. Ki=0 为什么还叫 PID 模块？

- **一句话回答：** 模块能力是通用 PID，实例配置是 PD，两者层次不同。
- **项目实现：** Controller 支持 P/I/D 与积分模式，v1.0.1 的最终参数选择禁用 I。
- **为什么这样设计：** 复用完整控制器，同时诚实描述当前配置。
- **继续优化：** 文档统一写“PID controller, final PD configuration”。

### Q43. D 项为什么需要滤波？

- **一句话回答：** 微分会放大测量噪声，未经滤波会让 PWM 对小波动敏感。
- **项目实现：** derivative alpha 0.2，非有限值、dt 和输出均检查。
- **为什么这样设计：** 保留变化率阻尼作用，同时限制高频噪声。
- **继续优化：** 用固定机械输入和频谱评估不同 cutoff，而非只比较肉眼效果。

### Q44. Anti-Windup 是什么？

- **一句话回答：** 输出饱和时限制积分继续累积，防止退出饱和后长时间恢复。
- **项目实现：** PID 模块有积分上下限和积分模式；最终 Ki=0，所以当前积分 windup 实际不活跃。
- **为什么这样设计：** 通用模块要覆盖未来真实闭环，但不能假装当前正在使用积分。
- **继续优化：** 机械平台上比较 conditional integration、back-calculation 和 leaky integral。

### Q45. 为什么输出只有 ±10 µs？

- **一句话回答：** 当前目标是安全、可重复的小幅姿态响应，不是搜索 SG90 极限。
- **项目实现：** PID 相对中心限制 ±10 µs，外层仍有 1450–1550 µs 绝对 clamp。
- **为什么这样设计：** 软件错误、参数变化和人工输入都不能直接产生大动作。
- **继续优化：** 机械平台和负载明确后，再通过安全标定评估范围。

### Q46. 1450–1550 µs 怎么确定？

- **一句话回答：** 它是 Phase 9A 无负载实机验证后的保守安全窗口，不是 SG90 全行程规格。
- **项目实现：** 最小/中心/最大固化在 ActuatorService 和 ConfigStore 校验。
- **为什么这样设计：** 演示优先避免撞限、堵转和供电风险。
- **继续优化：** 具体机构上用限位、角度反馈和电流监测重新标定。

### Q47. 为什么不能说外部机械姿态闭环？

- **一句话回答：** 因为 SG90 输出不会反向改变同一 MPU6500 测得的姿态。
- **项目实现：** MPU6500 是手持命令输入，PID 输出映射到舵机；没有 plant feedback edge。
- **为什么这样设计：** 控制理论术语必须与信号拓扑一致，不能因用了 PID 就称闭环稳定。
- **继续优化：** 把 IMU 装在舵机驱动平台上或增加编码器，再定义闭环指标。

### Q48. SG90 本身是不是闭环？

- **一句话回答：** 舵机内部通常有位置伺服，但项目没有读取其内部反馈，不能替代系统外层反馈。
- **项目实现：** STM32 只输出 PWM 并维护命令/安全状态，没有轴角遥测。
- **为什么这样设计：** 内部器件闭环与项目被控变量闭环是两个层次。
- **继续优化：** 外加编码器测量实际输出角，建立可观测 plant。

### Q49. 54.4% 到底是什么？

- **一句话回答：** 是人工输入对比中 PWM 输出标准差从 5.555 µs 到 2.535 µs 的下降。
- **项目实现：** `(5.555-2.535)/5.555 ≈ 54.4%`，来源是 `pid-config-comparison.csv`。
- **为什么这样设计：** 明确测量对象，避免把软件输出统计夸成机械性能。
- **继续优化：** 用固定输入台、编码器和示波器分别测命令、轴角和电气 PWM。

### Q50. Deadband 1.0° 的作用和代价？

- **一句话回答：** 它抑制零位附近噪声驱动，但引入小误差不响应区。
- **项目实现：** relative angle 在 ±1.0° 内 effective error 置零，并统计进出 deadband。
- **为什么这样设计：** 手持演示更重视中心稳定和安全，不追求不存在的机械稳态误差为零。
- **继续优化：** 在真实平台上用 hysteresis 或连续非线性映射比较响应与抖动。

## F. Protocol / IoT / Engineering（10 题）

### Q51. CRC16 有什么作用？

- **一句话回答：** 检测传输中的位错误和错误帧组合，不提供身份认证或加密。
- **项目实现：** Binary Protocol 和 Flash record 均使用 CRC16-CCITT-FALSE，但覆盖对象不同。
- **为什么这样设计：** 算法简单、跨 C/Python 易做 golden vector，适合小帧。
- **继续优化：** 不可信网络使用 TLS/MAC；不要把 CRC 当安全机制。

### Q52. 为什么不用 JSON 直接串口？

- **一句话回答：** 二进制帧更省 F103 的 Flash/RAM/解析开销，边界和类型也更确定。
- **项目实现：** 固定 header、length、sequence、CRC；JSON 只在 Python/MQTT 层产生。
- **为什么这样设计：** MCU 负责实时和确定性，Gateway 负责可读模型和网络。
- **继续优化：** 若 MCU 资源升级且人机直连需求提高，再量化比较 CBOR/JSON。

### Q53. Protocol 如何处理半帧、粘包和错帧？

- **一句话回答：** 流式 parser 累积候选帧，按 length/CRC 完成，错误后重新同步。
- **项目实现：** DMA 字节批量输入 parser，sequence 匹配响应，错误分类计数。
- **为什么这样设计：** 串口没有消息边界，read 一次不等于一帧。
- **继续优化：** 扩充随机 chunk、噪声插入和超长 payload fuzz。

### Q54. MQTT 为什么使用 QoS 1？

- **一句话回答：** 对状态/命令需要 Broker 确认，但接受可能重复并通过 request_id 去重。
- **项目实现：** topic contract 分 telemetry/state/command QoS，命令有 duplicate cache。
- **为什么这样设计：** QoS 2 开销更大，QoS 0 对关键命令缺少确认；QoS 1 是折中。
- **继续优化：** 公网和多 Broker 场景重新做故障模型与端到端确认。

### Q55. 为什么拒绝 retained 控制命令？

- **一句话回答：** 防止设备或 Gateway 重连时自动执行历史动作。
- **项目实现：** retained command 在到达设备前拒绝并计数，状态 topic 才允许 retained。
- **为什么这样设计：** 控制意图具有时效性，不能像设备在线状态一样长期保存。
- **继续优化：** 高风险动作再加短 expiry、nonce 和人工确认。

### Q56. request_id 去重解决什么？

- **一句话回答：** 解决 QoS 1 重投、客户端重试或网络恢复导致的同一动作重复执行。
- **项目实现：** Gateway 使用固定容量、带 TTL 的 cache，重复请求返回已有结果而不重发副作用命令。
- **为什么这样设计：** “消息至少一次”不等于“动作只执行一次”。
- **继续优化：** 跨进程重启需要持久化幂等记录或服务端事务，目前仅本地原型范围。

### Q57. Broker 掉线为什么不影响 PID？

- **一句话回答：** PID 在 STM32 SensorTask 100 Hz 本地执行，MQTT 只是配置和观测。
- **项目实现：** Gateway 串口断开/Broker 中断时 MCU 任务继续，Phase 10 验证本地 update_count 增长。
- **为什么这样设计：** 网络不确定性不能进入实时控制路径。
- **继续优化：** 明确配置租约和离线策略，但实时 loop 仍留在设备端。

### Q58. 双槽 Flash 为什么比单槽安全？

- **一句话回答：** 新记录提交前保留上一有效槽，掉电半写仍可回退。
- **项目实现：** 两个 1 KiB Slot，CRC、generation、commit marker，真实 power cycle 已验证。
- **为什么这样设计：** 单槽原地擦写在擦除或写入中断时可能只剩损坏记录。
- **继续优化：** 增加磨损统计或更高耐久存储，但保持事务语义。

### Q59. CRC、commit marker、generation 各解决什么？

- **一句话回答：** CRC 判断内容正确，marker 判断提交完成，generation 判断哪个有效槽更新。
- **项目实现：** marker 最后写入；启动扫描两个槽并校验 Schema/CRC/commit，再比较 generation。
- **为什么这样设计：** 三者正交，缺一项都会留下损坏、半写或新旧选择歧义。
- **继续优化：** 处理 generation wrap 并做形式化状态转换测试。

### Q60. 项目最大的不足是什么？

- **一句话回答：** 最大不足是没有真实机械反馈对象，控制指标只能停留在姿态输入到 PWM 输出链。
- **项目实现：** 项目主动标注外环不存在、Phase 8 `REFERENCE_LIMITED`、PWM jitter 未测、本地 MQTT 无 TLS。
- **为什么这样设计：** 当前阶段优先把有限硬件做成可验证工程，不用文档制造不存在的能力。
- **继续优化：** 单轴机械平台 + 编码器/第二 IMU，其次是可溯源参考、更高资源 MCU 和 TLS/ACL。
