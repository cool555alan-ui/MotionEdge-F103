# 面试追问链

以下 10 组追问按“结论—依据—边界—改进”逐层深入。回答中的数字统一来自 `docs/project_metrics.json`。

## 1. 项目本质与闭环边界

1. **这是什么项目？** 基于 STM32F103、MPU6500、SG90 和 MQTT 的姿态感知与物联网控制平台。
2. **闭环闭在哪里？** 姿态测量进入 PID，PID 输出驱动舵机，形成姿态驱动的执行器控制链。
3. **舵机会调整传感器位置吗？** 不会；当前机构中 SG90 不带动 MPU6500。
4. **那为什么仍称闭环控制？** 控制计算用实时姿态作为反馈输入，持续更新执行器输出；这是信号/控制链闭环，不是外部机械姿态闭环。
5. **能叫自平衡系统吗？** 不能，缺少舵机对被测对象姿态的机械反馈作用。
6. **怎样升级为机械闭环？** 把 IMU 固定在舵机驱动的平台上，建立目标姿态、机械传递、负载与扰动模型后重新辨识和调参。

## 2. MPU6500 与姿态融合

1. **为什么不用纯加速度计？** 静态可估倾角，但运动时线性加速度会污染结果。
2. **为什么不用纯陀螺仪？** 短时响应好，但零偏积分会导致长期漂移。
3. **采用了什么融合？** 互补滤波，以加速度低频参考约束陀螺积分。
4. **频率是多少？** 传感器与控制路径按 100 Hz 运行，物联网遥测按 10 Hz 展示。
5. **精度如何？** 对有限 iPhone 参考，Roll/Pitch MAE 为 0.352°/0.375°。
6. **这个结论能泛化吗？** 不能；参考设备不确定度未知、角度点和姿态覆盖有限，因此结论为 **REFERENCE_LIMITED**。

## 3. 为什么最终是 PD

1. **实现的是 PID 还是 PD？** 控制器模块支持 P/I/D，最终实测配置是 Kp=1.0、Ki=0、Kd=0.05，即 PD。
2. **为什么 Ki 为 0？** 当前是姿态到舵机响应演示，没有必须消除的机械稳态误差；积分反而可能积累偏差并饱和。
3. **D 项有什么作用？** 对变化趋势提供阻尼，降低输出抖动。
4. **如何避免 D 项放大噪声？** 使用 0.2 的导数滤波系数，并把控制增量限制在 ±10 µs。
5. **效果如何量化？** P 与 PD 的 PWM 标准差分别为 5.555 µs 和 2.535 µs，下降 54.4%。
6. **为什么不宣称最优？** 数据来自有限人工输入轨迹，属于 HUMAN_INPUT_LIMITED；若机构改变需要重新辨识。

## 4. 实时调度设计

1. **为什么引入 FreeRTOS？** 把传感器、控制、通信与维护活动分离成可观测的周期任务和事件路径。
2. **最关键的周期是什么？** 传感器/控制 100 Hz，通信 500 Hz，遥测 10 Hz，健康状态 1 Hz。
3. **如何证明频率达标？** 实测约为 100.003、500.012、10.001 和 1.000 Hz。
4. **如何看调度异常？** 记录任务心跳、deadline miss、栈溢出与 malloc failure 等健康量。
5. **长期运行结果？** 独立 600 s soak 中栈溢出和 malloc failure 均为 0。
6. **还有什么不足？** 现有结果覆盖单一硬件与有限负载；可加入 CPU load、调度延迟分布和更长 soak。

## 5. 通信协议与 DMA

1. **串口为什么不用文本协议？** 二进制帧更紧凑，字段和错误检测更明确，也便于机器解析。
2. **怎样处理粘包和错位？** 接收端在环形缓冲区中找帧头，依据长度解析，并用 CRC 拒绝损坏帧。
3. **UART 接收是否使用 DMA？** 是，使用 512 B circular DMA 接收，再由解析层消费。
4. **为什么 I2C 没继续上 DMA？** MPU6500 是短小、固定周期读取，当前 100 Hz 预算充足；引入 DMA 会增加状态机和错误恢复复杂度。
5. **怎样防止坏命令？** 协议层校验长度、CRC、命令和参数范围，执行器层仍保留安全约束。
6. **下一步如何增强？** 增加协议模糊测试、DMA 溢出统计、版本协商和串口噪声注入测试。

## 6. 执行器安全

1. **为什么需要 Arm？** 上电默认不允许输出，只有显式授权后执行器才进入可控状态。
2. **安全窗口是多少？** 当前实测控制使用 1450–1550 µs，中心为 1500 µs。
3. **PID 能否突破窗口？** 不能；PID 增量先限幅到 ±10 µs，执行器层还有绝对 PWM 约束。
4. **传感器掉线怎么办？** 控制路径失去新鲜姿态后进入安全状态，停止持续控制输出。
5. **ESTOP 做什么？** 立即禁止控制并使执行器回到安全状态；演示结束也执行 ESTOP。
6. **还可怎样提升？** 增加独立硬件急停、舵机电源隔离、机械限位和外部看门狗。

## 7. MQTT 与边云协同

1. **云端是否参与 100 Hz 控制？** 不参与；实时姿态与 PID 在 STM32 本地执行。
2. **MQTT 负责什么？** 上传姿态/健康数据，接收受控配置和操作命令，供 Node-RED 展示。
3. **为什么这样分层？** 网络延迟和断连不可预测，不能成为本地安全控制的必要条件。
4. **数据链可靠性如何？** 稳定区间网关与 Node-RED 均收到 4934/4934 帧，观测丢失为 0。
5. **延迟是多少？** 同机网关到 Node-RED 的 P95 为 2 ms；PING 命令 RTT 约 216.6 ms，二者不是同一指标。
6. **断网后怎样？** 本地控制继续；Broker 恢复实测约 2.80 s，公网性能不由该结果代表。

## 8. 参数持久化

1. **为什么需要持久化？** 让经确认的运行参数跨复位/断电恢复，减少每次部署重复配置。
2. **存在哪里？** Flash 末端保留 2048 B，地址为 0x0800F800–0x0800FFFF。
3. **怎样避免半写数据被采用？** 记录包含 schema、序列和完整性校验，加载时只选择有效记录。
4. **如何兼容升级？** 当前 schema=1；后续通过显式 schema 迁移而不是猜测旧布局。
5. **验证过断电吗？** 完成真实断电恢复测试，另用 FakeFlash 做故障注入。
6. **有什么边界？** 未宣称无限写寿命；后续可加入磨损计数、双页轮换和电压监测。

## 9. 资源与发布工程

1. **为什么关注资源瘦身？** STM32F103C8T6 的 Flash/RAM 有限，调试能力也必须留有余量。
2. **v1.0.1 Debug 占用？** Flash 59240 B，RAM 17824 B。
3. **Release 占用？** Flash 54296 B，RAM 17824 B。
4. **相对基线省了多少？** Debug Flash 减少 3068 B。
5. **如何防止回退？** CI 中检查固件尺寸、主机测试、阶段检查、文档与发布清单。
6. **P2 为什么不改固件？** v1.0.1 已冻结；本阶段只把事实、证据、讲解和演示工程化。
